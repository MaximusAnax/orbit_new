# dresscast — EVALS

## 1. What this product lives or dies on

Two capabilities, per SCOPE.md:

- **H1 — Day-long thermal layering.** Given an hourly forecast, the engine
  must pick garments whose *configuration range* (layers on/off) tracks the
  hour-by-hour required insulation — the cold-morning/warm-afternoon
  problem — while honoring precipitation and wind protection. If the
  physics is wrong (clo math, feels-like, required insulation) or the
  layer planning is weak, the product recommends being cold, wet, or
  sweating, and nothing else about it matters.
- **H2 — Wardrobe-constrained outfit quality over time.** Real value
  requires that outputs are *valid outfits from this closet, day after
  day*: never dirty items, never occasion violations, coherent colors and
  formality, no repeat of yesterday, and the whole eligible wardrobe in
  rotation — without sacrificing H1. A generator that nails comfort but
  cycles the same three outfits, or that quietly ignores the hamper, is
  not worth shipping.

Everything else (garment CRUD, import/export, suggestion staging, API/CLI
plumbing) is covered by ordinary pytest unit/integration tests, not eval
gates.

All evals are hermetic: offline adapters only, committed fixtures, no
network, no wall clock (all dates/timestamps are fixture literals),
deterministic outputs (the engine's core path is randomness-free; `seed` is
recorded but unused by default per SCOPE.md D12).

## 2. A note on circularity, and how we avoid it

The engine implements a physical model plus a domain rulebook, so a naive
eval ("does the engine match its own formulas?") risks testing the code
against itself. The suite splits four ways:

- **External-truth conformance (M1):** feels-like values are checked
  against *published* NWS/Environment Canada wind-chill chart values and
  Bureau of Meteorology apparent-temperature worked examples, transcribed
  by hand into a fixture with source labels; garment clo presets are
  checked against hand-transcribed ASHRAE 55 table rows. The truth was
  printed by someone else before this project existed.
- **Spec-pinning (rest of M1):** the D2/D3 constants (ensemble regression,
  required-clo anchors such as the definitional 1.0 clo at 21 °C / 1 met)
  are pinned via hand-computed golden cases, authored with a calculator
  and a rationale string, never generated by engine code. These are
  regression gates against silent constant drift.
- **Live-computed references (M2b, M3):** optimality and layering-advantage
  metrics compare the engine against exhaustive brute-force enumeration
  performed *at eval time* by a separate reference implementation in
  `evals/metrics.py` — recomputed, never stored, so it cannot go stale.
- **Independent rule checker (M4):** hard-constraint compliance is
  verified by a standalone validator in `evals/metrics.py`, written
  directly from the SCOPE.md HC-1…HC-8 text and deliberately *not*
  importing the engine's own constraint functions. A bug shared by both
  implementations would have to be written twice.

## 3. Metrics

Vocabulary: for a scenario `s` (wardrobe + day forecast + request params +
history) and an outfit `o`, `plan(o, s)` is the FR-8 hourly plan;
`inband(o, s)` = fraction of wear-window hours with |deviation| ≤ 0.25 clo;
`top1(s)` is the engine's rank-1 outfit. The scenario suite `S` has 12 day
scenarios (§4) × 2 wardrobes (small, medium) = 24 cases; `S_swing ⊂ S` is
the 8 cases whose scenario is flagged `swing: true` (diurnal feels-like
range ≥ 9 °C).

### M1 — physics_conformance (H1)

Over the golden physics table (fixture `physics_golden.json`, ~60 cases):

```
M1 = (# cases passing) / (# cases)
```

Case families and pass rules:

- Wind chill vs published chart: engine feels-like within ±0.5 °C of the
  NWS/EC chart value (e.g., −10 °C at 20 km/h → −17.9 °C; 0 °C at
  30 km/h → −6.6 °C). ~14 grid points, both unit systems' canonical rows.
- Steadman AT worked examples: within ±0.5 °C. ~6 cases, including a
  humid 30 °C case and a dry 35 °C case.
- Boundary behavior: T = 10.1 °C or v = 4.8 km/h → no wind chill applied;
  T = 25.9 °C → no AT applied (exact pass/fail).
- Garment presets: category preset clo equals the hand-transcribed ASHRAE
  value exactly (~15 rows, source-labeled).
- Ensemble regression: hand-computed `0.835·Σ + 0.161` for 6 ensembles,
  |engine − expected| ≤ 1e-9; empty set → 0.
- Required-clo anchors: (21 °C, met 1.0) → 0.997; (22 °C, met 1.1) →
  0.714; clamps at both ends; windproof attenuation (wp 2 at 15 km/h →
  effective 4.5 km/h → no wind chill). |engine − expected| ≤ 1e-3.

### M2 — comfort_fit (H1)

```
M2 = mean over s in S of inband(top1(s), s)
M2_worst = min over s in S of inband(top1(s), s)
```

### M2b — exact_optimality_ratio (H1 + search quality)

Ground truth at eval time: brute-force enumeration of *every* HC-valid
outfit (no candidate caps, no pruning) on the small wardrobe (≤ ~12k
outfits; reference implementation in `evals/metrics.py`), each evaluated
with the full per-hour configuration selection, taking
`best(s) = max_o inband(o, s)`:

```
ratio_s = inband(top1(s), s) / best(s)        (defined as 1.0 when best = 0)
M2b_mean = mean over small-wardrobe s of ratio_s
M2b_min  = min  over small-wardrobe s of ratio_s
```

This is the anti-cap check: SCOPE.md D12's candidate caps and bound-pruning
must not cost real quality.

### M3 — layering_advantage (H1, the hard part isolated)

For swing cases, compare against the best *static* dressing — the best
single fixed configuration worn all day, chosen with full hindsight.
Brute-force at eval time over all HC-valid outfits `o` and all
configurations `c` of `o`, wearing `c` for every hour (rain-cover rules
still enforced):

```
static_best(s) = max over (o, c) of inband_static(o, c, s)
M3 = mean over s in S_swing of [ inband(top1(s), s) − static_best(s) ]
```

`static_best` is a *strong* opponent (hindsight-optimal single ensemble);
beating it by a wide margin is only possible by actually planning layer
changes across the day. This isolates H1's layering skill from everything
else.

### M4 — hard_constraint_compliance (H2)

Over every outfit the engine emits anywhere in the eval suite (24 scenario
cases × k=3, plus all 14 rollout days × k=3, plus the edge-wardrobe cases):
the independent checker (§2) verifies HC-1…HC-8 (slot coverage and role
compatibility, cleanliness, occasion membership, formality spread, no
duplicates, rain-hour cover adequacy incl. umbrella wind cap, leg-base
gating, no-repeat vs fixture history), plus: every relaxation actually
applied appears in `compromises` (an unflagged relaxation counts as a
violation), and stored `score_total` equals the weighted recomputation from
`scores` (±1e-9).

```
M4 = 1 − (# violations) / (# checks)
```

### M5 — palette_style_auc (H2)

Over the golden combination set (fixture `color_style_golden.json`, ~60
hand-authored outfits labeled `good` / `bad` / `borderline` with
rationales). Using the engine's combined soft score
`q(o) = 0.5·S_color(o) + 0.5·S_style(o)`:

```
M5 = ( Σ_{g∈good} Σ_{b∈bad} [q(g) > q(b)] + 0.5·[q(g) = q(b)] )
     / (|good|·|bad|)
```

Borderline cases are excluded from the AUC (they document intended
near-boundary behavior for reviewers) but are printed in the scorecard.
Anti-gaming companion: `neutral_auc`, the same AUC computed with the naive
scorer `q'(o)` = fraction of items that are all-neutral — reported and used
by the M5b margin gate.

### M6 — rollout_variety_and_coverage (H2)

One 14-day simulated rollout (medium wardrobe, `rollout_14d.json` weather,
`schedule.json` occasions + laundry on days 7 and 14). Each day: recommend
(k=3), auto-wear rank 1, apply FR-4 side effects; laundry days reset dirty
items. Let `W_d` = day d's worn core-item set, `E` = the fixture's
`eligible_rollout` garment id list:

```
repeat_free  = 1.0 if W_d ≠ W_{d−1} for all d in 2..14 else 0.0
consec_sim   = mean over d in 2..14 of |W_d ∩ W_{d−1}| / |W_d ∪ W_{d−1}|
utilization  = |∪_d W_d ∩ E| / |E|
rollout_comfort = mean over d of inband(worn outfit_d, day_d)
```

### M7 — determinism (FR-18, guards everything)

On 3 scenario cases and the full rollout: run the recommendation twice with
identical inputs → serialized Recommendations (outfits, plans, reasoning)
byte-identical; recompute `score_total` and every `hour_plan` number from
stored inputs → matches stored values exactly; wardrobe hash stable across
runs.

```
M7 = 1.0 if all checks pass else 0.0
```

### Report-only metrics (printed, not gated)

- **Edge-wardrobe degradation:** on `edge.json` (no waterproof outer, no
  umbrella) × rainy scenarios: fraction of runs that correctly emit
  compromises or a structured `infeasible_wardrobe` with the right missing
  capability named. Diagnostic for FR-15 UX; correctness itself is gated
  inside M4 (unflagged relaxation = violation).
- **Component contributions:** mean of each score component across top-1
  outfits (watches for a component collapsing to constant).
- **Baseline table:** `mean_static` and `random_valid` values of M2/M6
  quantities (see §5) for eyeballing the margins.
- **`shed_count`:** mean number of configuration changes per day on
  `S_swing` (sanity: should be ≥ 1, typically 2).

## 4. Fixture strategy

Everything lives in `evals/fixtures/`, is deterministic, and is committed.
No real photos, no personal data; all wardrobes and weather are synthetic.

```
evals/fixtures/
  physics_golden.json        # M1: hand-transcribed chart values + hand-computed cases,
                             #     each with {inputs, expected, tolerance, source, rationale}
  color_style_golden.json    # M5: labeled outfit combos with rationales
  wardrobes/
    small.json               # 26 garments, hand-authored (see below)
    medium.json              # ~70 garments, generated (seed 42), hand-reviewed
    edge.json                # 18 garments with deliberate gaps (no rain shell, one footwear)
  weather/
    01_winter_calm.json      # 12 day scenarios (below), hand-authored hourly series
    ...
    12_autumn_windy_mild.json
    rollout_14d/day_01.json … day_14.json
  history/
    scenario_history.json    # wear history injected before scenario runs (yesterday's outfit etc.)
  rollout/
    schedule.json            # per-day occasion, laundry days, eligible_rollout id list
  generate.py                # seeded generator for medium.json + rollout weather (committed)
  expected.json              # generator/author-measured baseline stats (informational)
```

- **`physics_golden.json`** — every case carries a `source` string (e.g.,
  `"NWS wind chill chart, T=-10C v=20km/h"`, `"ASHRAE 55 garment table:
  long-sleeve shirt"`, `"hand calc: 0.835*1.58+0.161"`) so a reviewer can
  verify any row against the public document or a calculator without
  running code.
- **Wardrobes.** `small.json` is hand-authored to be *complete but tight*:
  6 base tops, 4 mids, 4 outers (incl. one waterproof-2 shell and one
  parka), 5 bottoms, 1 leg base, 3 footwear, 3 accessories (umbrella, hat,
  gloves) — spanning formality 1–4 and all occasions, every clo at its
  category preset. Small enough for exhaustive brute force (≤ ~12k valid
  outfits/scenario) yet able to dress every scenario. `medium.json` is
  generated by the committed seeded script with realistic composition
  (~30% tops, colors drawn 60% neutral per capsule-wardrobe practice) and
  hand-reviewed; regeneration is a reviewed change. `edge.json` omits rain
  cover and spare footwear on purpose to exercise FR-15.
- **Weather scenarios.** Hand-authored 24-hour series using the standard
  diurnal shape (minimum near sunrise, maximum mid-afternoon — sinusoid
  with scenario-specific amplitude), each with metadata
  `{swing: bool, description, designed_to_catch}`:
  1. `winter_calm` (−6→−2 °C, 5 km/h) — deep-cold sizing, gloves/hat advisory
  2. `winter_windy` (−4→0 °C, 30–45 km/h) — wind chill + windproof value
  3. `winter_snow` (−2→1 °C, p 0.7, 1–3 mm/h) — cold + cover interplay
  4. `spring_swing` (5→18 °C, dry) — the canonical shed-layers day *(swing)*
  5. `spring_swing_windy_am` (4→16 °C, 25 km/h before 10:00) — config-dependent feels-like *(swing)*
  6. `fall_swing_rain_pm` (7→14 °C, p 0.8 from 15:00, 3 mm/h) — plan must hold cover late *(swing)*
  7. `cold_rain_allday` (4→7 °C, p 0.9, 2–6 mm/h) — the nastiest day; warmth AND waterproofness
  8. `mild_drizzle` (12→15 °C, p 0.45, 0.5 mm/h) — soft-penalty band, no hard requirement
  9. `summer_hot` (24→33 °C, uv 8) — clo floor + UV advisory
  10. `summer_thunderstorm` (22→30 °C, p 0.7 14:00–17:00, 12 mm/h) — the warm-rain trap: shell not coat, umbrella insufficient (heavy) *(swing)*
  11. `shoulder_mild_steady` (14→18 °C) — easy day; sanity that nothing weird happens
  12. `autumn_windy_mild` (10→15 °C, 35 km/h) — wind protection without cold; umbrella wind cap
- **History.** `scenario_history.json` plants yesterday-worn outfits so
  HC-8 and variety scoring are exercised in every scenario run, not only
  the rollout.
- **`expected.json`** — the author/generator records, per scenario case:
  brute-force `best(s)`, `static_best(s)`, `mean_static` and
  `random_valid` baseline values. Informational anchors for reviewing gate
  levels; gates are asserted only against live-computed values, so
  `expected.json` can never mask a regression.

**Ground truth summary:** M1 truth = published charts/tables + hand
calculation; M2b/M3 truth = exhaustive brute force recomputed at eval time;
M4 truth = independent rule checker; M5 truth = hand-authored labels from
color/formality practice (SCOPE.md D8/D9 sources); M6 truth = construction
of the rollout. No gated metric's truth is produced by the code path under
test.

## 5. Baselines and gates

Two naive baselines are computed live inside the eval run (they share the
engine's physics for evaluation, so comparisons are apples-to-apples):

- **`mean_static`** — the "check the weather app once" strategy: same hard
  filters (HC-1…HC-7; no variety), then pick the outfit minimizing
  |Icl(all layers) − required_clo(mean feels-like over the window)|, worn
  in full all day (single configuration; rain rules still applied when
  possible). Ties → lexicographic. This is what a sensible person without
  hourly planning does.
- **`random_valid`** — mean over 20 seeded draws of HC-valid outfits worn
  in full all day.

Predicted levels (derived from scenario construction; author-measured
values frozen into `expected.json` at fixture-authoring time — the build
phase must reconcile any drift before gates are finalized in code review):

| Strategy | M2-style comfort (mean inband) | Why |
|---|---|---|
| random_valid | ≈ 0.30–0.45 | valid ≠ warm-enough; ensemble clo is roughly uniform over ~0.5–1.6 vs a ±0.25 band |
| mean_static | ≈ 0.60–0.75 | perfect at the daily mean, but a swing day's requirement spans ~0.9–1.1 clo (range × 0.082 clo/°C at met 1.6) while a ±0.25 band covers 0.5 — roughly half the hours fall out |
| static_best (hindsight) on S_swing | ≈ 0.50–0.65 | same band-coverage arithmetic, best case |
| engine target | ≥ 0.90 | a 3-config outfit spans ~0.6–1.5 clo and re-selects hourly |

For M5, `neutral_auc` (fraction-neutral scorer) is expected ≈ 0.60–0.75:
the goldens are authored so that neutrals help but hue-relation judgments
(analogous vs clash) decide many pairs; random scoring sits at 0.50 by
construction of AUC.

| Gate | Threshold | Rationale |
|---|---|---|
| M1 physics_conformance | = 1.00 | Finite lookups against published charts and hand calcs; any miss is a bug, not noise. |
| M2 comfort_fit | ≥ 0.90 | ~0.2 above `mean_static` (≈ 0.68 predicted): the product's core claim is hourly planning beats daily-mean dressing. Not 1.0 because tight wardrobes legitimately leave a few shoulder hours slightly out of band (e.g., the 07:00 case in DATA_MODEL.md §6 at −0.26 clo). |
| M2_worst | ≥ 0.75 | No scenario may collapse: even `cold_rain_allday` with the small wardrobe must keep ¾ of hours in band. |
| M2b_mean | ≥ 0.97 | Candidate caps + pruning may cost ≤ 3% comfort vs exhaustive search; below that the "bounded enumeration" story is broken. |
| M2b_min | ≥ 0.90 | No single scenario may fall off a cliff (guards bound/tie-break bugs). |
| M3 layering_advantage | ≥ +0.20 | Predicted engine ≈ 0.90 vs hindsight-static ≈ 0.58 on swings (gap ≈ 0.32); gating at +0.20 leaves head-room for fixture evolution while making the metric impossible to pass without genuine layer planning — a static-dresser scores ≤ 0 *by definition*. |
| M4 hard_constraint_compliance | = 1.00 | Constraint violations are trust-destroying (a single dirty-item or missed-rain recommendation ends daily use). Compliance is engineered, not statistical — so the gate is exact. |
| M5 palette_style_auc | ≥ 0.90 | Far above random (0.50); below 1.0 because ~10% of authored pairs sit deliberately near rule boundaries (triadic vs clash edges). |
| M5b anti-gaming margin | M5 − neutral_auc ≥ 0.10 | Proves hue-relation and formality logic carry real ranking weight; a count-the-neutrals regression cannot pass. |
| M6 repeat_free | = 1.00 | The owner's verbatim requirement ("don't repeat yesterday") is a constraint; one violation in 14 days is a failure. |
| M6 consec_sim | ≤ 0.40 | Sharing a coat and boots on consecutive winter days is fine (Jaccard ≈ 0.3 at outfit size 5); re-wearing most of the outfit is not. 0.40 permits the former, blocks the latter. |
| M6 utilization | ≥ 0.60 | With laundry cycling, ~60% of the eligible closet in 14 days means variety pressure actually rotates the wardrobe; `mean_static` (no variety term) measures ≈ 0.25–0.35 because it replays its favorite valid outfit until laundry forces change. |
| M6 rollout_comfort | ≥ 0.85 | Variety must not buy freshness with discomfort; allowed 0.05 below M2 because history constraints shrink the choice set. |
| M7 determinism | = 1.00 | CONVENTIONS.md hermeticity; also what makes every other number trustworthy. |

Gates are asserted on live-computed values inside the eval run — never
against `expected.json`.

## 6. How the suite runs

Mirrors `orbit-backend/evals/`:

- **`evals/metrics.py`** — `MetricResult(name, value, gate, passed,
  detail)`, `EvalReport`, the independent HC checker, the brute-force
  reference enumerator, the two baselines, AUC/ratio helpers, and the
  rollout simulator (drives the real services layer against an in-memory
  store).
- **`evals/run.py`** — `python -m` runnable with zero configuration and no
  network. Loads fixtures, runs M1–M7 plus report-only metrics through the
  offline adapters and pure engine, prints a scorecard: one line per
  metric with value, gate, PASS/FAIL, and detail (per-scenario inband
  fractions, baseline values, worst offender), then a JSON summary. Exit
  code 0 iff all gates pass.
- **`evals/test_gates.py`** — pytest gates: one test per gate in §5, test
  names carrying FR ids (e.g., `test_fr9_layering_advantage_gate`,
  `test_fr10_fr15_compliance_gate`), each calling the metric functions
  directly (not via subprocess), plus `test_eval_runner_passes` executing
  `run.py` end-to-end and asserting exit code 0. `uv run pytest
  dresscast/` therefore fails on any quality regression.

Runtime budget: full suite < 30 s on a laptop. Largest cost: brute force on
the small wardrobe — ≤ ~12k outfits × 16 hours × ≤ 6 configs ≈ 1.2M
hour-evaluations per scenario, vectorizable to well under a second each,
× 12 scenarios; plus the 14-day rollout (14 engine runs on the medium
wardrobe).
