# dresscast — EVALS

> Revision 2 (post-review); audit trail in `REVIEW.md`. Two blockers drove the
> rewrite of §3 and §5: every gated comfort metric measured `inband`, a purely
> thermal quantity, while the engine ranks on a five-component objective — so a
> "ThermalBot" that ignored 60% of the product passed every gate; and `inband`
> was not reachability-aware, making the M2 family arithmetically impossible on
> five of the committed scenarios. §5.2 works that arithmetic and §3 replaces
> the metrics.

## 1. What this product lives or dies on

Two capabilities, per SCOPE.md:

- **H1 — Day-long thermal layering.** Given an hourly forecast, the engine
  must pick garments whose *configuration range* (layers on/off) tracks the
  hour-by-hour required insulation — the cold-morning/warm-afternoon
  problem — while honoring precipitation and wind protection, and must say
  so plainly when the closet cannot reach the day. If the physics is wrong
  (clo math, feels-like, required insulation) or the layer planning is weak,
  the product recommends being cold, wet, or sweating, and nothing else
  about it matters.
- **H2 — Wardrobe-constrained outfit quality over time.** Real value
  requires that outputs are *valid, well-put-together outfits from this
  closet, day after day*: never dirty items, never occasion violations,
  coherent colors and formality, no repeat of yesterday, and the whole
  eligible wardrobe in rotation — without sacrificing H1. A generator that
  nails comfort but cycles the same three clashing outfits, or that quietly
  ignores the hamper, is not worth shipping.

Everything else (garment CRUD, suggestion staging, API/CLI plumbing) is
covered by ordinary pytest unit/integration tests, not eval gates.

All evals are hermetic: offline adapters only, committed fixtures, no
network, no wall clock (all dates/timestamps are fixture literals),
deterministic outputs (the engine's core path is randomness-free; `seed` is
persisted but has no effect, SCOPE.md D12). The one deliberate RNG is the
`random_valid` baseline's private `random.Random(0)` (§5.1).

## 2. A note on circularity, and how we avoid it

The engine implements a physical model plus a domain rulebook, so a naive
eval ("does the engine match its own formulas?") risks testing the code
against itself. The suite splits five ways, and each gated metric is labelled
with which kind of truth it rests on:

- **External-truth conformance (M1, two families):** feels-like values are
  checked against *published* Environment Canada wind-chill chart cells and
  Bureau of Meteorology apparent-temperature worked examples, transcribed by
  hand with source labels; garment clo presets are checked against
  hand-transcribed ASHRAE 55 table rows; and a **calibration family** checks
  `required_clo` against the definitional 1 clo point and ASHRAE 55's two
  published comfort-zone centres at ±0.30 clo (SCOPE.md D3's residual table).
  The truth was printed by someone else before this project existed.
- **Spec-pinning (rest of M1):** the D2/D3 constants and the FR-5 ramps are
  pinned via hand-computed golden cases, authored with a calculator, each
  carrying its arithmetic in a `rationale` string, never generated by engine
  code. These are regression gates against silent constant drift — **not**
  external validation, and §3 labels them as such. *(Revision 1 mislabelled
  the required-clo anchors as external truth and attached a false ASHRAE
  provenance to one of them.)*
- **Live-computed references (M2b, M2c, M3, M8):** optimality, saturation,
  layering-advantage and per-component capability compare the engine against
  exhaustive brute-force enumeration performed *at eval time* by a separate
  reference implementation in `evals/metrics.py` — recomputed, never stored,
  so it cannot go stale.
- **Independent rule checker (M4, M9, M10):** constraint compliance, output
  well-formedness, score consistency, accessory attachment, explanation
  coverage and degradation correctness are verified by a standalone validator
  in `evals/metrics.py`, written directly from the SCOPE.md text and
  deliberately **not** importing `engine.comfort`, `engine.protection`,
  `engine.palette`, `engine.style`, `engine.variety` or `engine.assemble`.
  It implements its own feels-like, `required_clo`, `Icl`, and its own
  `S_color`/`S_style`/`S_variety`/`S_protect`/`S_thermal` (~120 lines total).
  A bug shared by both implementations would have to be written twice.
- **Expert-labelled, partially spec-derived (M5):** the `color_style_golden`
  labels are hand-authored by the same author who wrote D8/D9, so they
  partly restate the rule table. This is acknowledged rather than claimed
  away. It is mitigated three ways: every case carries a `source` string
  naming an *external* basis (a capsule-wardrobe or dress-code convention),
  not the D8 zone it lands in; at least one third of good/bad pairs must be
  decided by something other than the Δh bucket; and M5b requires a margin
  over three trivial scorers, not one.

**Ground-truth summary:** M1 = published charts/tables + hand calculation;
M2b/M2c/M3/M8 = exhaustive brute force recomputed at eval time; M4/M9/M10 =
independent rule checker; M5 = expert labels with external sources and an
anti-triviality margin; M6 = construction of the rollout plus a live-computed
baseline; M7 = self-consistency by design. No gated metric except M5 draws
its truth from a document written alongside the engine, and M5 says so.

## 3. Metrics

Vocabulary. For a scenario `s` (wardrobe + day forecast + request params +
history) and an outfit `o`: `plan(o, s)` is the FR-7 hourly plan;
`S_thermal(o, s)` is FR-6.4's aggregate; `inband(o, s)` is the fraction of
wear-window hours with `|deviation| ≤ 0.25` **against the achievable target**
(FR-6.2 — this is the change that makes the metric reachable at temperature
extremes); `total(o, s)` is FR-8's weighted objective; `top1(s)` is the
engine's rank-1 outfit.

The scenario suite `S` has **15 day scenarios (§4) × 2 wardrobes (small,
medium) = 30 cases**. `S_small ⊂ S` is the 15 small-wardrobe cases (the only
ones brute force runs on — see §6). `S_swing ⊂ S_small` is the **6** cases
flagged `swing: true`; `summer_thunderstorm` is deliberately *not* among them
(§4). Three parameter-variation cases extend `S_small` for M4(j) only.

### M1 — physics_conformance (H1) — external truth + spec-pinning

Over the golden physics table (fixture `physics_golden.json`, **exactly 58
cases**):

```
M1 = (# cases passing) / 58
```

| Family | Cases | Truth kind | Pass rule |
|---|---|---|---|
| Wind chill vs Environment Canada °C chart | 14 | external | engine feels-like within ±0.5 °C of the chart's **integer** cell (e.g. −10 °C @ 20 km/h → chart −18, formula −17.861; 0 °C @ 30 km/h → chart −6, formula −6.473). Cells are transcribed verbatim; no one-decimal "chart" values are invented |
| Steadman AT worked examples | 6 | external | within ±0.5 °C; includes a humid 30 °C and a dry 35 °C case |
| Ramp continuity + validity boundaries | 6 | spec-pinning | `feels` is Lipschitz-3 in T across both ramp edges (`|f(T₁)−f(T₂)| ≤ 3·|T₁−T₂|`; worst measured 2.41 at 10.0→10.1 °C @ 45 km/h, vs **44** in revision 1); `v ≤ 4.8 km/h` → zero wind delta; `T ≥ 14` → zero wind delta; `T ≤ 24` → zero heat delta |
| Garment presets vs ASHRAE 55 rows | 15 | external | exact equality, each row source-labelled |
| Ensemble regression `0.835·Σ+0.161` | 6 | spec-pinning | hand-computed, `|engine − expected| ≤ 1e-9`; empty set → 0 |
| Required-clo spec anchors | 8 | spec-pinning | `|engine − expected| ≤ 1e-3`. Includes **(21 °C, met 1.0) → 0.997** and **(22 °C, met 1.1) → 0.724** *(revision 1 pinned 0.714, which is what the formula gives with Ia = 0.71, not the documented 0.70 — a correct implementation failed the gate and the tempting "fix" was to bend Ia)*; both clamps; met scaling; windproofness-2 attenuation (15 → 4.5 km/h → no wind delta) |
| External calibration | 3 | external | `required_clo` vs published clo/temperature pairs at **±0.30 clo**: (21.0, 1.0) vs 1.000; (21.75, 1.1) vs ASHRAE 55 winter zone 1.000; (24.5, 1.1) vs ASHRAE 55 summer zone 0.500. SCOPE.md D3 tabulates the residuals (worst −0.246) and explains why the anchors are not simultaneously satisfiable |

Every case's `rationale` string carries its arithmetic verbatim (e.g.
`"(34-22)/(7.66*1.1)-0.70 = 0.72416"`), so a reviewer can catch an
arithmetic error without running code — the class of error that put a wrong
value into revision 1 under a `= 1.00` gate.

### M2 — comfort_fit (H1) — the engine's own thermal objective

```
M2       = mean over s in S of S_thermal(top1(s), s)
M2_worst = min  over s in S of S_thermal(top1(s), s)
```

`S_thermal` is the FR-6.4 aggregate (exposure-weighted mean blended with the
worst hour), measured against the achievable target, so it is well-defined
and non-degenerate on every scenario including the saturated ones. Reported
beside it, ungated: `inband(top1(s))` per scenario, and `saturated_hours(s)`
— the count of wear-window hours where the target was clamped — so a reviewer
can see exactly how much of each day was physically unreachable.

### M2b — search_optimality (H1 + search quality)

The anti-cap check: SCOPE.md D12's candidate caps and bound-pruning must not
cost real quality. It therefore measures **the objective the engine actually
maximizes**, not a thermal proxy:

```
ratio_s  = total(top1_pruned(s), s) / total(top1_exhaustive(s), s)
M2b_mean = mean over s in S_small of ratio_s
M2b_min  = min  over s in S_small of ratio_s
```

`top1_exhaustive` runs the *same* engine scoring over the full HC-valid
enumeration with candidate caps and the bound-pruner disabled. *(Revision 1
computed `inband(top1)/max_o inband(o)`. The engine does not maximize
`inband` — thermal carries 0.40 against 0.60 of colour/style/variety/
protection — so a perfectly correct engine failed it whenever it traded a
little comfort for a much better palette, and a pruning bug that cost only
colour quality was invisible to it. Revision 1 also defined `best = 0 →
ratio = 1.0`, which handed a free pass on exactly the five saturated
scenarios.)*

### M2c — saturation_maximality (H1, the extremes)

On the hours where FR-6.2's clamp is active there is no in-band answer; the
only meaningful correctness statement is "wear the most/least the closet
allows". Over `S_small`, for every wear-window hour whose `clamped` field is
non-null:

```
M2c = (# clamped hours where Icl(top1's config_h) equals the brute-force
        max (ceiling) or min (floor) achievable by any HC-valid outfit-config
        for that hour, to 1e-6)
      / (# clamped hours)
```

`metrics.py` asserts the denominator is ≥ 40 across the suite (guaranteed by
scenarios 01/02/03/09/10), so the metric can never be vacuously 1.0.

### M3 — layering_advantage (H1, the hard part isolated)

Opponent: the **thermally static dresser** — the best fixed core ensemble
worn in a single fixed configuration all day, chosen with full hindsight,
where the rain cover (outer shell or the umbrella) *may* be donned for
rain/soft-rain hours and doffed after, but **no layer may be added or shed
for temperature**. *(Revision 1's opponent had to keep the shell on all 15
hours on rain days, so on half of `S_swing` it measured "the engine takes the
shell off when it stops raining" rather than layer planning.)*

```
static_best(s) = max over (o, c) of inband_static(o, c, s)
M3     = mean over s in S_swing of [ inband(top1(s), s) − static_best(s) ]
M3_min = min  over s in S_swing of [ ... ]
```

`inband` (not `S_thermal`) is used here because the differential against a
static dresser is the product's headline claim and the binary band makes the
gap legible. `S_swing` is **small-wardrobe only** (6 cases) — revision 1
required medium-wardrobe exhaustive enumeration that §6's runtime budget
never accounted for, which would have forced a bounded substitute and made
`static_best` an under-estimate, biasing M3 upward.

### M4 — output_validity (H1 + H2) — independent checker

Over every outfit the engine emits anywhere in the suite (30 scenario cases ×
k=3, the 3 parameter-variation cases, all 3 × 14 rollout days × k=3, and the
edge-wardrobe cases), the independent checker (§2) runs these families. Every
check is exact; the metric is the pass fraction and the gate is 1.00.

| # | Family | What is checked |
|---|---|---|
| a | Hard constraints | HC-1…HC-8: slot coverage and role compatibility, cleanliness, occasion membership, formality spread, no duplicates, rain-hour cover adequacy incl. the umbrella wind cap, leg-base gating on `bare_feels_c`, no-repeat vs fixture history |
| b | `rank_completeness` | exactly `min(k, |feasible set|)` outfits, ranks contiguous from 1; `|feasible set|` from brute force on `S_small` |
| c | `rank_monotonicity` | `score_total` non-increasing in rank |
| d | `topk_diversity` | pairwise core-item Jaccard ≤ 0.5 between returned outfits, unless a `compromise` records the relaxation |
| e | `score_consistency` | `score_total` = weighted recomputation from `scores` (±1e-6) **and** the checker's own `S_thermal`, `S_protect`, `S_color`, `S_style`, `S_variety` match the stored `scores` (±1e-6). This is what closes the "compute the honest score for reporting, rank on something else" hole |
| f | `accessory_attachment` | FR-9's attachment rules reproduced independently: exact accessory set, exact classes, slots filled in ascending garment-id order; an unfired class attaches nothing |
| g | `explanation_coverage` | the set of `reasoning` classes equals the set of FR-15 triggers the checker finds fired — an unexplained rain window and an advisory for a rule that did not fire are both violations |
| h | `plan_smoothness` | ≥ 2 distinct configurations on every `S_swing` case; ≤ `MAX_CONFIG_CHANGES` (3) changes on every case; `MIN_DWELL_HOURS` (2) respected; segment compression lossless |
| i | `relaxation_flagging` | every relaxation applied appears in `compromises`; `compromises` non-empty ⟹ the zero-feasible precondition genuinely held (brute-forced on `S_small`); `1 ≤ n < k` recorded as a `partial_k` **note**, never as a compromise |
| j | `parameter_response` | on `spring_swing` × small: met 1.2 ⇒ mean worn `Icl` strictly greater than at met 1.6; met 2.2 ⇒ strictly less; wear window 17:00–22:00 ⇒ the plan contains exactly those hours and scoring reads no others |
| k | `quantization` | every serialized float equals its own rounding to the declared DP (FR-19) |

```
M4 = 1 − (# violations) / (# checks)
```

### M5 — palette_style_auc (H2)

Over `color_style_golden.json` — **exactly 60 hand-authored outfits: ≥ 24
labelled `good`, ≥ 24 `bad`, the remainder `borderline`**, each with a
rationale and an external `source`. With `q(o) = 0.5·S_color(o) +
0.5·S_style(o)`:

```
M5        = AUC(good vs bad) under q      (ties count 0.5)
M5_color  = AUC(good vs bad) under q = S_color
M5_style  = AUC(good vs bad) under q = S_style
M5_mono   = ( mean q(good) − mean q(borderline),
              mean q(borderline) − mean q(bad) )
M5b       = M5 − max(neutral_auc, formality_only_auc, hue_only_auc)
```

Borderline cases are excluded from the AUC but are **not** consequence-free:
`M5_mono` requires them to sit where their rationales say they do. The three
trivial scorers are `neutral_auc` (fraction of items that are all-neutral),
`formality_only_auc` (formality spread alone — the cheapest cheat, since
HC-4-style mismatches are the obvious thing to label bad) and `hue_only_auc`
(Δh bucket alone). The scorecard prints M5's standard error alongside the
value so the gate can be read with its uncertainty.

### M6 — rollout_variety_and_coverage (H2)

**Three** independent 14-day rollouts (A/B/C), differing in weather sequence
(generated by the committed seeded script, seeds 101/102/103), occasion
schedule, and starting history; medium wardrobe; laundry on days 7 and 14.
Each day: recommend (k=3), auto-wear rank 1, apply FR-3 side effects. Let
`W_d` = day d's worn core-item set.

`E`, the eligible set, is **computed by rule inside `metrics.py`**, not read
from a fixture: every non-retired garment in the wardrobe whose `occasions`
intersect the schedule's occasion set and whose `layer_role` is a core role.
*(Revision 1 read a hand-authored `eligible_rollout` list, so the one gated
metric guarding wardrobe rotation had a denominator the fixture author could
shrink to pass it. The key is deleted from `schedule.json`.)* `metrics.py`
asserts `|E| ≥ 40` and prints the exact value.

```
no_repeat_window_3 = fraction of d in 4..14 with W_d ∉ {W_{d-1}, W_{d-2}, W_{d-3}}
novel_item_rate    = mean over d in 4..14 of |W_d \ (W_{d-1} ∪ W_{d-2} ∪ W_{d-3})| / |W_d|
consec_sim         = mean over d in 2..14 of |W_d ∩ W_{d-1}| / |W_d ∪ W_{d-1}|
utilization        = |(∪_d W_d) ∩ E| / |E|
rollout_comfort    = mean over d of S_thermal(worn outfit_d, day_d)
```

Every M6 gate is asserted on the **worst of the three rollouts**, so a single
tuned sequence cannot carry the metric. `repeat_free` (yesterday) is reported
only, not gated: HC-8 makes it a restatement of a hard constraint already
verified at exactly 1.00 by M4(a), so gating it measured nothing.

### M7 — determinism (FR-19, guards everything)

Canonical serialization for comparison: `json.dumps(obj, sort_keys=True,
separators=(',',':'))` after dropping the fields that are non-deterministic
by design — **`id`, `created_at`, `fetched_at`, `snapshot_id`** (named here so
"determinism" cannot quietly become "a subset I chose"). Four checks, on 3
scenario cases and all 3 rollouts:

1. two runs with identical inputs → byte-identical serialization;
2. `score_total` and every `hour_plan` number recomputed from stored inputs →
   identical to the stored values;
3. `wardrobe_hash` stable across runs **and** unchanged when the request's
   occasion filter changes (FR-19 makes it request-independent);
4. **ULP robustness:** perturb `temp_c`, `wind_kmh` and `humidity_pct` by one
   ULP on one scenario → the ranking is unchanged and every serialized value
   is unchanged. This is the property FR-19's quantization exists to buy, and
   it is what makes the cross-platform claim honest given that `v**0.16` and
   `exp()` are libm-dependent.

```
M7 = 1.0 if all checks pass else 0.0
```

### M8 — component_capability (H2) — the anti-ThermalBot gate

Nothing in revision 1 inspected the colour, style, protection or variety
quality of an *engine-emitted* outfit: M5 graded the scoring functions in
isolation and M4 only checked internal consistency. A degenerate engine that
ranked on `(inband desc, variety desc)` while storing the honest weighted
score for reporting passed every gate. For each component
`c ∈ {protection, color, style, variety}`, over `S_small`:

```
lift_c = ( mean_s c(top1(s))          − mean_s c(random_valid(s)) )
       / ( mean_s c(brute_max_c(s))   − mean_s c(random_valid(s)) )
```

where `brute_max_c(s)` is the maximum of component `c` over the exhaustive
HC-valid enumeration (already computed by the M2b reference pass, so this is
nearly free). Each component's numerator and denominator are printed.
`metrics.py` asserts every denominator ≥ 0.05; a smaller one means the
fixture cannot discriminate on that component and is a fixture bug, reported
as a hard failure rather than a silent `n/a`.

### M9 — protection_response (H1) — the soft half of FR-9

The hard half of FR-9 is gated by M4(a) via HC-6. The soft half — the part
that separates a useful product from a rule checker — had no gate on engine
output in revision 1, even though two scenarios were authored specifically to
exercise it. Over the cases where the wardrobe contains an option that is
adequate *and* HC-1…HC-5 compatible (determined by the checker, not
assumed):

| Case | Required response of `top1` |
|---|---|
| `mild_drizzle` (p 0.45) | carries waterproofness ≥ 1 worn, or the umbrella |
| `autumn_windy_mild`, `winter_windy`, `spring_swing_windy_am` (≥ 30 km/h) | outer with windproofness ≥ 1 worn during the windy hours |

```
M9 = (# applicable cases where top1 responds) / (# applicable cases)
```

`random_valid`'s rate on the same cases is printed beside it, so the number
can be read as a lift rather than an absolute.

### M10 — degradation_correctness (H2) — FR-14 gets teeth

Revision 1 left FR-14 report-only, arguing that M4's unflagged-relaxation
rule covered it. It does not: an engine that *never* relaxes and returns
`infeasible_wardrobe` immediately emits zero outfits, contributes zero checks
to M4's denominator, and scores 1.00 while being useless on exactly the days
the user most needs help. Over the `edge.json` × {5 rain scenarios, 3 winter
scenarios} matrix, plus any suite case where HC-1…HC-8 admits nothing:

| # | Check |
|---|---|
| a | the outcome is either a relaxed recommendation or a structured `infeasible_wardrobe` — never an empty success, never an unstructured error |
| b | when relaxed, the applied relaxations are exactly the lexicographically earliest ladder prefix that makes the problem feasible; the checker determines this by brute-forcing feasibility under R1, then R1+R2, then R1+R2+R3 |
| c | HC-1, HC-2, HC-3 and HC-5 hold in every relaxed outfit |
| d | `infeasible_wardrobe` names the capability whose absence the checker independently confirms, and carries a well-formed FR-16 `DayBrief` payload |

```
M10 = (# checks passed) / (# checks)
```

`relaxation_rate` — the fraction of *normal*-wardrobe suite runs that relaxed
anything — is printed so an engine that relaxes constantly on healthy
wardrobes is visible.

### Report-only metrics (printed, not gated)

- **Component contributions:** mean of each score component across top-1
  outfits (watches for a component collapsing to constant).
- **Baseline table:** every baseline value with mean ± sd, alongside the gate
  it backs.
- **Saturation:** `saturated_hours` per scenario, and the clamped-hour count.
- **Plan shape:** distribution of configuration changes per day and distinct
  configurations per day (the gated form of this lives in M4(h)).
- **`monotone_shed_delta`:** the score gap between the engine and a
  "start warmest, only ever shed" policy on `frontal_drop` and `midday_dip`.
  Authored to be materially positive; if it ever approaches zero those two
  fixtures have stopped doing their job.
- **`repeat_free`**, `|E|`, `relaxation_rate`, M5's borderline table.

## 4. Fixture strategy

Everything lives in `evals/fixtures/`, is deterministic, and is committed.
No real photos, no personal data; all wardrobes and weather are synthetic.

```
evals/fixtures/
  physics_golden.json        # M1: 58 cases, each {inputs, expected, tolerance,
                             #     truth_kind, source, rationale}
  color_style_golden.json    # M5: 60 labeled outfit combos with rationale + source
  wardrobes/
    small.json               # 26 garments, hand-authored (below)
    medium.json              # ~70 garments, generated (seed 42), hand-reviewed
    edge.json                # 18 garments with deliberate gaps (no rain shell, one footwear)
  weather/
    scenarios.toml           # the 15 scenario parameter blocks (hand-authored)
    01_winter_calm.json … 15_cold_snap_swing.json      # generated from scenarios.toml
    dst_spring_23h.json, dst_autumn_25h.json           # FR-4 only, not scenarios
    rollout_a/day_01.json … day_14.json                # seeds 101 / 102 / 103
    rollout_b/…  rollout_c/…
  history/
    scenario_history.json    # wear history injected before scenario runs
    rollout_{a,b,c}_history.json
  rollout/
    schedule_{a,b,c}.json    # per-day occasion + laundry days  (no eligible_rollout key)
  generate.py                # seeded generator: medium.json, the 15 scenario series
                             # from scenarios.toml, and the 3 rollout weather sets
  expected.json              # author-measured baselines and ceilings (informational only)
```

- **`physics_golden.json`** — every case carries `truth_kind` (`external` |
  `spec_pinning`), a `source` string (e.g. `"Environment Canada wind chill
  chart, T=-10C v=20km/h, cell -18"`, `"ASHRAE 55 garment table: long-sleeve
  shirt"`) and a `rationale` string containing the arithmetic. §3 M1 gives
  the exact per-family counts; `metrics.py` asserts the file has 58 cases and
  the stated family sizes, so the count and the breakdown cannot drift apart.
- **Wardrobes.** `small.json` is hand-authored to be *complete but tight*:
  6 base tops, 4 mids, 4 outers (incl. one waterproofness-2 shell and one
  parka), 5 bottoms, 1 leg base, 3 footwear, 3 accessories (umbrella, hat,
  gloves) — spanning formality 1–4 and all occasions, every clo at its
  category preset. Core enumeration is
  `6·5·3·(1+4+6)·(1+4)·(1+1) = 9,900` outfits before HC filtering;
  `metrics.py` asserts the brute-force enumerator produces exactly that
  closed-form count, so a fixture edit can never silently shrink the
  reference. Accessories are **not** an enumeration dimension (SCOPE.md FR-9
  attaches them deterministically after selection, and the umbrella is a
  single deterministic choice used by HC-6 adequacy) — this is why the count
  is 9,900 rather than revision 1's unreconciled "≤ 12k" or the 79,200 an
  accessory-enumerating reference would need. `medium.json` is generated by
  the committed seeded script with realistic composition (~30% tops, colors
  drawn 60% neutral per capsule-wardrobe practice) and hand-reviewed;
  regeneration is a reviewed change. `edge.json` omits rain cover and spare
  footwear on purpose to exercise FR-14/M10.
- **Weather scenarios.** Generated by `generate.py` from `scenarios.toml`,
  whose per-scenario parameter block is the hand-authored artifact (shape,
  amplitude, wind profile, precip window and intensity, uv peak, occasion,
  flags). Hand-authoring 15 × 24 rows by hand was a real cost in revision 1's
  plan and bought nothing. Shapes: `diurnal` (sinusoid, minimum near sunrise),
  `ramp_down` (frontal passage) and `dip` (rain-cooled midday trough) — the
  last two exist because **all twelve of revision 1's scenarios were
  monotone-up-then-down sinusoids, on which the trivial policy "start
  warmest, only ever shed" is optimal**, and D6's LIFO chain makes that policy
  the natural implementation. Each file carries
  `{shape, swing, occasion, description, designed_to_catch}`.

  | # | Scenario | Profile | Occasion | Flags |

## 5. Baselines and gates

### 5.1 Baselines (computed live inside the eval run)

Both share the engine's physics for evaluation, so comparisons are
apples-to-apples, and both are fully specified — revision 1's definitions
were not reproducible.

- **`mean_static`** — the "check the weather app once" strategy: same hard
  filters (HC-1…HC-7, no variety), then pick the outfit minimizing
  `|Icl(all layers worn) − required_clo(mean bare_feels_c over the wear
  window, met)|`, worn in full all day (single configuration; rain rules
  applied when a compliant configuration exists). **Feels-like is pinned to
  windproofness 0**, which removes revision 1's circularity (its "mean
  feels-like" depended on the configuration that had not been chosen yet).
  Ties → ascending garment-id tuple.
- **`random_valid`** — rejection sampling from the per-slot candidate lists
  using a dedicated `random.Random(0)` instance (never the global RNG, per
  CONVENTIONS.md hermeticity), resampling on any HC-1…HC-7 violation with a
  10,000-attempt cap, **200 draws** per case (revision 1 used 20, which is
  noise over a space of ~10⁴), worn in full all day. Mean ± standard
  deviation is reported for every quantity it baselines.

### 5.2 Why revision 1's gates were impossible, and what changed

Working SCOPE.md D1's presets through D2 and D3 for `small.json`: the warmest
legal ensemble is `flannel 0.34 + 2×0.36 mids + parka 0.70 + thick trousers
0.24 + leg base 0.15 + boots 0.10 = Σ 2.25` → `Icl = 2.040`; the coolest is
`tee 0.08 + shorts 0.08 + sandals 0.02 = Σ 0.18` → `Icl = 0.311`. With D5's
±0.25 band, an outfit can be **absolutely** in band only when
`required_clo ∈ [0.061, 2.290]`, i.e. bare feels-like in **[−2.65 °C,
+24.67 °C]** at met 1.6. Five of the twelve committed scenarios sat outside
that window for most of their wear hours (both winters, `winter_snow`'s cold
end, `summer_hot`, `summer_thunderstorm`), so `inband` was identically 0 for
*every possible outfit* on those days: `M2 ≥ 0.90` and `M2_worst ≥ 0.75` were
unsatisfiable by construction, and `M2b`'s `best = 0 → ratio = 1.0`
convention turned the same days into free passes. The predictable resolutions
during the build phase were both bad: lower the gates to whatever got built,
or inflate fixture clo beyond the preset table (a 0.49-clo flannel), which
would have broken M1's preset family and destroyed transfer to real
wardrobes.

The fix is in SCOPE.md FR-6.2/D17, not in the gate levels: the per-hour
target is clamped into the achievable band, comfort is scored against that,
the raw shortfall is reported and explained to the user, and M2c gates
maximality on the clamped hours so "clamped" cannot mean "anything goes".
`S_thermal` (graded, never identically zero) replaces raw `inband` in the
absolute gate; `inband` survives where a differential is what is claimed
(M3).

### 5.3 Gate-setting protocol (binding)

Revision 1 said the build phase "must reconcile any drift before gates are
finalized", with every baseline given as an unmeasured range. That is an
escape hatch: the arithmetic above guaranteed drift, and nothing constrained
its direction. The protocol is now a one-way ratchet:

1. The levels in §5.4 are **predictions** derived from §5.2's arithmetic and
   the scenario construction. They are labelled as such.
2. Before any gate is finalized in code, `evals/run.py` is executed on the
   committed fixtures and the **measured** baseline values replace the
   predicted ranges in §5.4. This happens before the engine is optimized
   against them.
3. A gate may be **raised** at any time.
4. A gate may be **lowered** only by first changing the fixture or the model
   and re-deriving the baseline. Lowering a gate to accommodate a measured
   implementation score is prohibited and must be rejected in code review,
   with the reason recorded in REVIEW.md.
5. Every gate with a baseline is asserted **twice** in `test_gates.py`: as an
   absolute, and as a margin over the live-computed baseline. If the measured
   baseline turns out stronger than predicted, the margin assertion tightens
   the gate automatically.
6. The scorecard prints, for every gate, the value, the gate, the baseline,
   and the margin.

## 6. How the suite runs

Follows the workspace eval convention:

- **`evals/metrics.py`** (≈ 450 lines) — `MetricResult(name, value, gate,
  baseline, margin, passed, detail)`, `EvalReport`, the independent checker
  (~120 lines, its own physics and its own five component scorers, importing
  nothing from `engine/` except `models`), the brute-force reference
  enumerator, the two baselines, AUC/ratio helpers, and the rollout simulator
  (drives the real services layer against an in-memory store).
- **`evals/run.py`** (≈ 110 lines) — `python -m` runnable with zero
  configuration and no network. Loads fixtures, runs M1–M10 plus the
  report-only metrics through the offline adapters and pure engine, prints a
  scorecard: one line per metric with value, gate, baseline, margin,
  PASS/FAIL and detail (per-scenario `S_thermal`/`inband`/`saturated_hours`,
  baseline values, worst offender), then a JSON summary. Exit code 0 iff all
  gates pass.
- **`evals/test_gates.py`** (≈ 140 lines) — one test per gate in §5.4, test
  names carrying FR ids (e.g. `test_fr8_layering_advantage_gate`,
  `test_fr9_fr14_compliance_gate`), each calling the metric functions
  directly (not via subprocess), each asserting both the absolute and (where
  §5.4 has one) the margin, plus `test_eval_runner_passes` executing `run.py`
  end-to-end and asserting exit code 0. `uv run pytest dresscast/` therefore
  fails on any quality regression.

**Runtime budget: full suite < 30 s on a laptop, in pure Python with no
numpy.** The arithmetic, stated honestly this time:

- Brute force runs on `S_small` only (15 cases). Raw core enumeration is
  9,900 outfits; after HC-2/HC-3/HC-4/HC-7 filtering the HC-valid count is
  ~1,500–3,000 per scenario (printed, and its closed-form pre-filter count
  asserted).
- Accessories are not an enumeration dimension (SCOPE.md FR-9), so there is
  no ×8 blow-up on rain days; the umbrella is one deterministic item entering
  HC-6 adequacy as a flag.
- Per outfit the ≤ 6 configurations are totally ordered in `Icl` (D6's LIFO
  chain), and `required_clo` is memoised per `(hour, windproofness class)` —
  45 values per scenario. Selecting each hour's configuration is therefore a
  ≤ 3-comparison walk over a sorted 6-list, not a 6-way scan: ~45 operations
  per outfit-day.
- Reference cost ≈ 3,000 × 45 ≈ 135k operations per scenario, ×15 ≈ 2M — well
  under a second in total. One pass computes everything M2b, M2c, M3 and M8
  need.
- Plus 3 × 14 = 42 engine runs on the medium wardrobe for the rollouts, and
  the M1/M5 golden tables (pure lookups).

If a future fixture makes brute force expensive, the sound factorisation is
to keep enumerating core outfits and treat protection as a per-hour overlay —
never to reduce the enumeration's coverage.
