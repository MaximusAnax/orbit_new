# flowlist — EVALS

## 1. What this product lives or dies on

Two capabilities, per SCOPE.md:

- **H1 — Transition-scoring fidelity.** The pairwise score must agree with
  real DJ practice: harmonic (Camelot) compatibility, beatmatchable tempo
  distance with half/double-time folding, energy continuity, loudness
  matching. If the score calls a clash seamless (or vice versa), every
  downstream ordering is confidently wrong.
- **H2 — Ordering optimization quality.** Given a correct score, the
  heuristic (multi-start greedy + Or-opt + 2-opt) must find orderings close to
  the true optimum and far above trivial strategies. A max-weight
  Hamiltonian-path solver that only marginally beats "sort by BPM" is not
  worth shipping.

Everything else (import, storage, API/CLI plumbing) is covered by ordinary
pytest unit/integration tests, not eval gates.

All evals are hermetic: offline adapters only, committed fixtures, seeded
randomness, no network, no wall clock (timestamps in fixtures are literals).

## 2. A note on circularity, and how we avoid it

The engine implements a domain rulebook, so a naive eval ("does the engine
match the rules?") risks testing the code against itself. We split the suite:

- **Spec-conformance metrics** (M1, M3) pin the engine to *externally
  documented* DJ practice — the Camelot compatibility chart and beatmatching
  tolerances — written down as *data* (golden tables authored by hand from the
  published guidance, with a rationale string per case, never generated by
  engine code). These are regression gates: they catch broken key math, wheel
  wraparound bugs, and weight/formula drift.
- **Behavioral metrics** (M2, M4–M7) test *emergent* behavior the rulebook
  does not directly encode: ranking labeled good/bad pairs where several
  components interact, and recovering near-optimal orderings against
  independent ground truth (exact Held-Karp solutions, planted constructions).
  Hard-coding the golden table would not move these.

## 3. Metrics

Component vocabulary: `S(a→b)` is the engine transition score (SCOPE.md FR-6);
an *ordering score* of permutation π over n entries is
`total(π) = Σ_{i=1..n−1} S(π_i → π_{i+1})` and `mean(π) = total(π)/(n−1)`.

### M1 — key_relation_accuracy (H1)

Over the golden key-relation table (fixture `key_relations.json`, ~72 cases):

```
M1 = (# cases where engine relation == expected relation
        AND |engine S_key − expected S_key| ≤ 1e-9) / #cases
```

Cases cover every named relation in SCOPE.md D2, both directions, both
letters, and wheel wraparound (12A→1A, 1B→12B), plus Camelot↔pitch-class
conversion round-trips for all 24 keys.

### M2 — pair_ranking_auc (H1)

Over labeled transition pairs (fixture `transition_pairs.json`; labels
`seamless` ≻ `workable` ≻ `clash`). For each ordered label pair (L₊, L₋) in
{(seamless, workable), (workable, clash), (seamless, clash)}:

```
AUC(L₊, L₋) = ( Σ_{x∈L₊} Σ_{y∈L₋} [S(x) > S(y)] + 0.5·[S(x) = S(y)] )
              / (|L₊|·|L₋|)
M2 = mean of the three AUCs
```

This is threshold-free (a pure ranking metric), so it cannot be gamed by
rescaling scores.

### M3 — component_monotonicity (H1)

Property sweeps, each a pass/fail check; `M3 = passed / total` over ~30 checks:

- Fixing all else, `S_bpm` is non-increasing as BPM deviation sweeps
  0→15% in 0.5% steps; equals 1.0 at ≤2%; equals 0 at ≥12%.
- Octave folding: `S(86→172 BPM)` within the folding penalty (×0.9) of
  `S(86→86)`; the `half_time` flag is set; `S(86→172)` > `S(86→150)`.
- `S_energy` non-increasing in |Δenergy|; under `build`, a −0.2 energy delta
  scores strictly lower than +0.2; `neutral` is symmetric.
- `S_loud` equals 1.0 for Δ≤2 dB, 0 for Δ≥10 dB, non-increasing between.
- Missing-field handling: null key on either side ⇒ key component exactly 0.5
  and `missing_key` flag present; total stays in [0,1].
- Weight algebra: with `weights = {bpm: 1.0, others: 0}`, `S == S_bpm`.

### M4 — exact_optimality_ratio (H2)

Over the small-instance suite (8 playlists, n = 8–12). Ground truth `total*`
is computed at eval time by Held-Karp dynamic programming
(`engine.optimizer.exact_optimal`, O(n²·2ⁿ), < 1 s at n=12) — recomputed, not
stored, so it can never go stale.

```
ratio_p = total(heuristic order for p) / total*(p)
M4_mean = mean_p ratio_p          M4_min = min_p ratio_p
```

### M5 — planted_chain_recovery (H2)

Over the planted-chain suite (6 playlists, n = 50–150). Each fixture is built
(committed seeded generator, §4) as a chain T₁→T₂→…→Tₙ whose consecutive
transitions are engineered to be excellent (mean ≈ 0.88), then shuffled with a
fixed seed. The planted chain's `mean(chain)` is a strong lower bound on the
achievable optimum (not necessarily the optimum itself, hence "recovery"
not "optimality"):

```
M5 = mean_p [ mean(heuristic order for p) / mean(planted chain for p) ]
```

### M6 — baseline_margin (H2)

Over the realistic messy suite (4 playlists, n = 30–80, mixed genres/tempos,
5% missing features). Three baselines are *computed live in the eval run*
(they share the engine's scoring, so the comparison is apples-to-apples):

- `identity`: the stored (shuffled) order,
- `random`: mean over 20 seeded shuffles (seeds 0–19),
- `bpm_sort`: ascending sort by BPM — the strongest naive strategy, since it
  buys tempo continuity and (through the generator's genre-realistic
  BPM–energy correlation) much of energy continuity for free.

```
M6 = mean_p [ mean(heuristic_p) − mean(bpm_sort_p) ]
```

### M7 — determinism (FR-15, guards both H1 and H2)

On 3 fixtures spanning all suites: run `reorder` twice with seed 7 →
orderings byte-identical; run with seed 8 → allowed to differ (no assert);
recompute each run's `after` aggregates from its per-transition breakdowns →
must match stored aggregates exactly.

```
M7 = 1.0 if all identity/consistency checks pass else 0.0
```

### Report-only metrics (printed, not gated)

- `worst_transition_improvement` = mean_p (min-score after − min-score
  before) on the messy suite. Diagnostic: the objective maximizes the sum, so
  we watch (not gate) the worst seam.
- `seamless_fraction_after` on the messy suite.
- `bpm_only_auc`: M2 recomputed with weights `{bpm:1}` — shows how much of
  the ranking skill comes from harmony vs tempo.

## 4. Fixture strategy

Everything lives in `evals/fixtures/`, is deterministic, and is committed. No
real audio, no copyrighted metadata dumps; all track metadata is synthetic
(invented titles/artists) with genre-realistic feature distributions.

```
evals/fixtures/
  key_relations.json        # M1 golden table (hand-authored)
  transition_pairs.json     # M2 labeled pairs (hand-authored)
  catalog.json              # ~200 synthetic tracks with features
  playlists/
    exact_XX.json           # 8 small instances (n=8–12), entry lists over catalog
    planted_XX.json         # 6 planted-chain instances (n=50–150) + planted order
    messy_XX.json           # 4 realistic mixed playlists (5% missing fields)
  generate.py               # seeded generator for catalog + playlists (committed)
  expected.json             # generator-measured baseline stats (informational)
```

- **`key_relations.json`** — hand-authored from the published Camelot
  compatibility chart (Mixed In Key's documented rules: same code, ±1 same
  letter, relative letter-swap, +2 energy boost, parallel-key, semitone
  lift). Each case: `{from: "8A", to: "9B", expected_relation: "diagonal",
  expected_score: 0.75, rationale: "Am→G: 6/7 shared tones, mode flip;
  MIK 'diagonal' advanced mix"}`. Authored once by hand; a reviewer can check
  any row against the public chart without running code.
- **`transition_pairs.json`** — ~120 hand-authored feature pairs labeled
  `seamless` / `workable` / `clash` with rationales. Labels follow published
  DJ guidance, deliberately mixing components so no single component predicts
  the label: e.g. perfect key but 14% BPM gap ⇒ `clash`; adjacent key at 4%
  BPM and +0.1 energy ⇒ `seamless`; relative key but 9 dB loudness jump ⇒
  `workable`. Includes ~12 pairs modeled on well-known real-world pairings
  (e.g. an 86 BPM hip-hop groove into a 172 BPM drum-and-bass track as the
  canonical half-time `workable/seamless` case); feature values are stored in
  the fixture itself, so ground truth is self-contained.
- **`catalog.json` + `playlists/`** — produced by `generate.py` with
  `--seed 42` and committed (regeneration is a reviewed change). Generator
  design:
  - Four genre clusters with realistic ranges — house 120–128 BPM /
    energy 0.6–0.9, drum-and-bass 170–178 / 0.7–0.95, hip-hop 82–96 /
    0.4–0.7, indie/pop 96–120 / 0.3–0.7; keys uniform over all 24 Camelot
    codes; loudness −14…−4 dB correlated with energy (louder masters are
    higher-energy, mirroring streaming-era mastering practice).
  - **Exact suite:** n=8–12 samples from 1–2 clusters. Small enough for
    Held-Karp ground truth at eval time.
  - **Planted suite:** chains constructed by walking the Camelot wheel with
    steps from {same, relative, ±1} and BPM steps ≤ 2%, energy drift ≤ 0.06
    per hop — by construction every planted transition scores ≥ 0.8 (mean
    ≈ 0.88, recorded per fixture in `expected.json`). The committed file
    stores both the planted order (ground truth) and the seeded shuffle the
    optimizer receives.
  - **Messy suite:** cross-cluster mixtures with 5% of feature fields nulled
    (seeded choice) to exercise missing-data handling under gating.
- **`expected.json`** — the generator also *measures* and records, per
  playlist: planted-chain mean, identity mean, 20-shuffle random mean,
  bpm-sort mean. These are informational anchors for reviewing gate levels;
  gates themselves are asserted against live-computed values (§5), so
  `expected.json` can never mask a regression.

**Ground truth summary:** M1/M2 truth = hand-encoded published practice;
M4 truth = exact DP recomputed at eval time; M5 truth = construction;
M6 truth = live-computed baselines. No metric's truth is produced by the
system under test.

## 5. Baselines and gates

Predicted baseline levels below follow from the generator design (feature
distributions → expected component scores); `generate.py` freezes the actual
measured values into `expected.json` at fixture-generation time, and the build
phase must reconcile any drift from these predictions before gates are
finalized in code review.

| Strategy (messy suite, mean transition score) | Expected level | Why |
|---|---|---|
| random order | ≈ 0.40–0.50 | random key relation ⇒ E[S_key] ≈ 0.35; cross-cluster BPM gaps mostly score 0 |
| identity (stored order) | ≈ random | stored order is a seeded shuffle |
| bpm_sort | ≈ 0.60–0.70 | near-perfect S_bpm + correlated energy, but keys stay random (E[S_key] ≈ 0.35) |
| heuristic (target) | ≥ bpm_sort + 0.08 | must win on harmony *and* tempo simultaneously |

For M2, the analogous naive scorer (`bpm_only_auc`) is expected ≈ 0.65–0.75
because the pair labels are authored so that key relations decide many cases;
a random scorer sits at 0.50 by construction of AUC.

| Gate | Threshold | Rationale |
|---|---|---|
| M1 key_relation_accuracy | = 1.00 | Finite lookup against the public chart; any miss is a bug, not noise. |
| M2 pair_ranking_auc | ≥ 0.90 | Far above random (0.50) and the bpm-only scorer (≈0.70); below 1.0 because a handful of authored `workable` cases sit deliberately on rule boundaries. |
| M2b anti-gaming margin | M2 − bpm_only_auc ≥ 0.10 | Proves the harmonic/energy/loudness components carry real ranking weight; a bpm-only regression cannot pass. |
| M3 component_monotonicity | = 1.00 | Properties are exact consequences of the formulas in SCOPE.md D3–D5; any failure is an implementation error. |
| M4_mean exact_optimality_ratio | ≥ 0.97 | TSP literature: greedy construction alone typically lands ~10–25% short of optimum; 2-opt closes to within ~5% on random instances. Multi-start + Or-opt on n ≤ 12 should do better still; 0.97 mean forces the local search to actually work. |
| M4_min | ≥ 0.90 | No single instance may fall off a cliff (guards degenerate anchor/tie-break bugs). |
| M5 planted_chain_recovery | ≥ 0.92 | The planted chain is recoverable in principle; allowing 8% slack acknowledges the heuristic may find a *different* near-optimal path. Random sits near 0.45/0.88 ≈ 0.51 on this ratio; bpm_sort near 0.75 (planted chains are key-coherent, which bpm_sort ignores). |
| M6 baseline_margin | ≥ +0.08 | The whole product claim: beat the best naive strategy by a clear margin (≈ one flag-level of quality per transition: 0.08 mean ≈ turning ~1 in 4 workable seams into seamless ones). Vacuous-pass check: bpm_sort itself scores margin 0. |
| M7 determinism | = 1.00 | CONVENTIONS.md hermeticity; also what makes every other number trustworthy. |

Gates are asserted on live-computed values inside the eval run — never against
`expected.json`.

## 6. How the suite runs

Mirrors `orbit-backend/evals/`:

- **`evals/metrics.py`** — `MetricResult(name, value, gate, passed, detail)`,
  `EvalReport`, AUC/ratio helpers, the live baseline implementations
  (`identity`, `random_shuffles`, `bpm_sort`).
- **`evals/run.py`** — `python -m` runnable with zero configuration and no
  network. Loads fixtures, runs M1–M7 plus report-only metrics through the
  offline adapters and pure engine, prints a scorecard: one line per metric
  with value, gate, PASS/FAIL, and detail (e.g. per-playlist ratios, baseline
  values), then a JSON summary. Exit code 0 iff all gates pass.
- **`evals/test_gates.py`** — pytest gates: one test per gate in §5 (test
  names carry FR ids, e.g. `test_fr8_exact_optimality_gate`), each calling the
  same metric functions directly (not via subprocess), plus
  `test_eval_runner_passes` which executes `run.py` end-to-end and asserts
  exit code 0. `uv run pytest flowlist/` therefore fails on any quality
  regression.

Runtime budget: full suite < 30 s on a laptop (largest cost: Held-Karp at
n=12 and 2-opt passes at n=150), so it runs in every CI invocation.
